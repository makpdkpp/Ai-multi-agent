# แผนการ Deploy — Multi-Agent AI Q&A Platform

## 1. หลักการ

Deploy ต้องทำได้บ่อยและปลอดภัย โดยไม่กระทบ agent ที่กำลังถูกใช้งานอยู่ (โดยเฉพาะ embed widget ที่ผู้ใช้ภายนอกเข้าถึงตลอดเวลา) ใช้หลัก **automate ทุกขั้นตอน** และ **แยก deploy code ออกจาก migrate ข้อมูล** เพื่อลดความเสี่ยง

## 2. CI/CD Pipeline

**เครื่องมือ:** GitHub Actions (หรือ GitLab CI ถ้าใช้ GitLab)

ขั้นตอนมาตรฐานต่อการ push code:

1. **Lint & unit test** — รันทุก PR ก่อน merge
2. **Build image** — build Docker image แต่ละ service (`api`, `worker`, `web`, `embed-widget`)
3. **Security scan** — scan image (Trivy) และ dependency (Dependabot/Snyk) หา vulnerability
4. **Push to registry** — เก็บ image ที่ container registry (GitHub Container Registry / ECR / GCR) พร้อม tag ตาม git commit SHA
5. **Deploy to staging** — auto-deploy ทุกครั้งที่ merge เข้า `main`
6. **Run agent evaluation suite** — รัน golden dataset (ตามแผนทดสอบข้อ 3) บน staging ก่อนอนุญาตให้ promote ไป production
7. **Deploy to production** — ทำแบบ manual approval (ต้องมีคนกด approve) ไม่ auto-deploy production ทันที

## 3. กลยุทธ์การ Deploy

- **Rolling update** เป็นค่าเริ่มต้นสำหรับ service ทั่วไป (`api`, `web`) — ทยอยแทนที่ pod ทีละตัว ไม่มี downtime
- **Blue-green deployment** สำหรับการเปลี่ยนแปลงที่มีความเสี่ยงสูง (เช่น เปลี่ยน coordinator/routing logic ครั้งใหญ่) — รันเวอร์ชันใหม่ขนานไปกับเวอร์ชันเก่า สลับ traffic เมื่อมั่นใจ แล้วค่อย decommission เวอร์ชันเก่า
- **Canary release** สำหรับการเปลี่ยน prompt หรือ LLM model ของ agent — ปล่อยให้ traffic ส่วนน้อย (เช่น 5-10%) ใช้ config ใหม่ก่อน วัดคุณภาพคำตอบเทียบกับ config เดิม แล้วค่อยขยาย

## 4. Database Migration

- ใช้เครื่องมือ migration (Alembic สำหรับ Python/SQLAlchemy) แยก migration ออกจากตัว deploy code
- กฎสำคัญ: migration ต้อง **backward-compatible** เสมอในระหว่าง rolling update (เช่น เพิ่มคอลัมน์ใหม่แบบ nullable ก่อน ค่อย backfill แล้วค่อยบังคับ not-null ใน migration ถัดไป) เพื่อไม่ให้ pod เวอร์ชันเก่ากับใหม่ที่รันพร้อมกันชั่วครู่ล่ม
- รัน migration เป็น step แยกก่อน deploy application version ใหม่เสมอ ไม่รวมไว้ใน container startup script

## 5. Secrets & Config ตอน Deploy

- Secret (DB credential, API key, encryption key) inject ผ่าน Vault/K8s Secret ไม่ฝังในไฟล์ image หรือ git repo
- แยก config ต่อ environment ผ่าน ConfigMap/environment variable ไม่ build image แยกต่อ environment

## 6. Embed Widget Deployment

- Widget JS bundle build แยกจาก backend, deploy ขึ้น **CDN** (CloudFront/Cloudflare) เพื่อ load เร็วบนเว็บลูกค้าและลดโหลดจาก backend โดยตรง
- Versioning ของ widget script (เช่น `widget.v2.js`) เพื่อให้ rollback ได้โดยไม่กระทบเว็บลูกค้าที่ฝัง script เวอร์ชันเก่าไว้อยู่ก่อนแล้ว

## 7. Health Check & Readiness

- ทุก service ต้องมี `/health` (liveness) และ `/ready` (readiness) endpoint
- Readiness probe ของ `api` ต้องเช็คว่าเชื่อมต่อ Postgres/Redis ได้จริงก่อนรับ traffic
- K8s ตั้ง `readinessProbe`/`livenessProbe` ให้ traffic ไม่ถูกส่งไป pod ที่ยังไม่พร้อม และ restart pod ที่ค้าง

## 8. Rollback Plan

- เก็บ image เวอร์ชันก่อนหน้าไว้ใน registry เสมอ (ไม่ลบทิ้งทันที) — rollback ทำได้ด้วยการสลับ tag กลับ
- ถ้า migration เป็น backward-compatible ตามข้อ 4 การ rollback code จะไม่ทำให้ schema เสียหาย
- กำหนด **rollback trigger** ชัดเจนล่วงหน้า เช่น error rate เกิน X% หรือ agent evaluation score ตกต่ำกว่าเกณฑ์หลัง deploy → auto-rollback หรือแจ้งทีมทันที

## 9. Deployment Checklist ต่อ Release

- [ ] ผ่าน CI ครบทุก stage (lint, test, security scan)
- [ ] ผ่าน agent evaluation suite บน staging
- [ ] Migration เป็น backward-compatible และทดสอบบน staging แล้ว
- [ ] แจ้งทีมที่เกี่ยวข้องล่วงหน้าถ้าเป็นการเปลี่ยนแปลงที่กระทบ embed widget สาธารณะ
- [ ] เตรียม rollback plan และรู้ trigger ที่จะสั่ง rollback ไว้ก่อน deploy จริง
- [ ] Monitor metric หลัง deploy อย่างใกล้ชิดอย่างน้อย 30-60 นาทีแรก

## 10. ความถี่ในการ Deploy

- **Staging:** auto-deploy ทุกครั้งที่ merge เข้า `main` (continuous)
- **Production:** เป็นรอบ (เช่น สัปดาห์ละ 1-2 ครั้ง) สำหรับการเปลี่ยนแปลงทั่วไป และ deploy แยกทันทีสำหรับ hotfix ด้านความปลอดภัยที่ critical
