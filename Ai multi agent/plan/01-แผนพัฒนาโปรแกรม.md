# แผนพัฒนาโปรแกรม — Multi-Agent AI Q&A Platform

## 1. ภาพรวมโครงการ

ระบบ multi-tenant web application ที่ให้ department admin สร้าง AI agent ของตัวเอง เชื่อมต่อกับข้อมูล MySQL, Excel หรือ PDF คู่มือสินค้า เลือก LLM ได้เอง (local หรือ OpenRouter) และให้บริการผ่านสองช่องทาง: chat ภายในองค์กร และ embed widget บนเว็บไซต์สาธารณะ

**Stakeholder หลัก:** super admin (ดูแลระบบ), department admin (สร้าง/จัดการ agent), พนักงานในแผนก (ใช้ internal chat), ผู้ใช้ภายนอกเว็บไซต์ (ใช้ embed widget)

## 2. สถาปัตยกรรมโดยสรุป

- **Orchestration:** FastAPI + LangGraph — coordinator agent route คำถามไปยัง SQL agent (MySQL), data agent (Excel/pandas), RAG agent (PDF) แล้ว synthesize คำตอบ
- **Metadata DB:** PostgreSQL (users, agents, data_sources, permissions, usage_logs) — ดู data model ที่ออกแบบไว้ก่อนหน้า
- **Vector store:** pgvector (ใน Postgres ตัวเดียวกัน) สำหรับ chunk ของ PDF
- **LLM layer:** เชื่อมผ่าน OpenAI-compatible interface เดียวกันทั้ง local (Ollama/vLLM) และ OpenRouter
- **Frontend:** Next.js สำหรับ admin panel + internal chat, lightweight JS widget แยกสำหรับ embed

## 3. Phase การพัฒนา

### Phase 0 — เตรียมโครงสร้างพื้นฐาน (2 สัปดาห์)
- ตั้งค่า repo, CI/CD, environment (dev/staging/prod)
- สร้าง Postgres schema ตาม data model ที่ออกแบบไว้ (users, departments, agents, data_sources, llm_configs)
- ตั้งค่า secret management (Vault/KMS) สำหรับ encrypt credential
- Auth system พื้นฐานด้วยบัญชีภายในสำหรับ Pilot (secure session/JWT, Argon2id, role-based: super_admin / department_admin / member)
- เตรียม data model ให้เพิ่ม Microsoft Entra ID/Microsoft 365 SSO ใน phase ถัดไปโดยไม่ต้องย้ายบัญชีผู้ใช้

**Deliverable:** โครงสร้าง backend ว่างที่ deploy ได้ พร้อม auth และ schema

### Phase 1 — Core agent engine (3-4 สัปดาห์)
- SQL agent: text-to-SQL + query validation + read-only sandbox ต่อ MySQL
- Data agent: อัปโหลด Excel → parse เป็น DataFrame → ให้ LLM เขียนโค้วิเคราะห์
- RAG agent: อัปโหลด PDF → chunk → embed → เก็บใน pgvector → retrieval
- Coordinator agent (LangGraph): route คำถามไปยัง agent ที่เหมาะสม, รวมคำตอบ
- รองรับเลือก LLM ต่อ agent (local/OpenRouter) ผ่าน config เดียว

**Deliverable:** เรียก API ถามคำถามกับ agent ตัวอย่าง 1 ตัว ได้คำตอบจากทั้ง 3 แหล่งข้อมูล

### Phase 2 — Multi-tenant admin panel (3 สัปดาห์)
- หน้า super admin: สร้าง department, สร้าง department admin, ภาพรวมระบบ
- หน้า department admin: สร้าง/แก้ไข agent, เชื่อมข้อมูล, เลือก LLM, ตั้ง system prompt
- Row-level isolation ตาม department_id (Postgres RLS หรือ enforce ที่ application layer)
- จัดการสิทธิ์สมาชิกในทีม (owner/editor/viewer)

**Deliverable:** admin panel ใช้งานได้ครบ ตรงกับ mockup ที่ออกแบบไว้

### Phase 3 — Internal chat + Embed widget (2-3 สัปดาห์)
- Internal chat UI: auth ผูกกับ user, ประวัติ conversation
- Embed widget: JS snippet ฝังเว็บได้, CORS/domain whitelist, rate limiting, anonymous session
- Prompt injection guard และการจำกัด scope คำตอบสำหรับ public widget

**Deliverable:** ฝัง widget ทดสอบบนเว็บตัวอย่างได้จริง

### Phase 4 — Token usage & billing (1-2 สัปดาห์)
- บันทึก `usage_logs` ทุกครั้งที่เรียก LLM (input/output tokens)
- ตาราง `model_pricing` และ engine คำนวณค่าใช้จ่าย
- Dashboard ค่าใช้จ่ายทั้งฝั่ง super admin (ภาพรวมทุกแผนก) และ department admin (เฉพาะแผนกตัวเอง)
- ระบบตั้งงบประมาณและแจ้งเตือนเมื่อใกล้/เกินงบ

**Deliverable:** dashboard การใช้งานและค่าใช้จ่ายตาม mockup

### Phase 5 — Hardening, testing, launch prep (2 สัปดาห์)
- ทำตามแผนความปลอดภัยและแผนทดสอบ (ไฟล์แนบ)
- Load testing, penetration testing เบื้องต้น
- เอกสารผู้ใช้ + training สำหรับ department admin

**Deliverable:** ระบบพร้อม production launch

## 5. ความเสี่ยงหลักที่ต้องติดตาม

- **ความแม่นยำของ text-to-SQL** กับ schema ที่ซับซ้อน — ต้องมี fallback ให้ผู้ใช้ยืนยัน/แก้ query ก่อนรัน
- **คุณภาพการ chunk เอกสาร PDF** ที่มีตาราง/รูปปนอยู่ — อาจต้องทดลองหลาย strategy
- **ต้นทุน LLM ที่ควบคุมไม่ได้** จาก public embed widget — ต้องมี rate limit และ budget cap ตั้งแต่ Phase 3
- **การรั่วไหลข้อมูลข้ามแผนก** — ต้องทดสอบ tenant isolation อย่างเข้มงวดก่อน launch
