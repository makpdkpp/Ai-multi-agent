# แผนความปลอดภัย — Multi-Agent AI Q&A Platform

## 1. ขอบเขตและหลักการ

ระบบนี้มีความเสี่ยงสูงกว่า chat application ทั่วไปเพราะ (1) เก็บ credential ฐานข้อมูลจริงของหลายแผนก (2) ให้ LLM รันคำสั่งที่แปลงมาจากภาษาธรรมชาติ (3) มีช่องทาง public-facing (embed widget) ที่คนนอกองค์กรเข้าถึงได้ หลักการออกแบบคือ **defense in depth**: ป้องกันหลายชั้น ไม่พึ่งการควบคุมจุดเดียว

## 2. การจัดการ Credential และข้อมูลลับ

| ประเด็น | มาตรการ |
|---|---|
| Password/API key ของ data source | Encrypt at rest ด้วย KMS/Vault แยกจาก database, ห้าม hardcode key ใน environment ที่ decrypt ได้ทุกที่ |
| ใครมีสิทธิ์ decrypt | เฉพาะ backend service ตอนเชื่อมต่อจริงเท่านั้น ไม่ log ค่า plaintext ที่ไหนทั้งสิ้น |
| MySQL connection | ใช้ user แบบ **read-only** เสมอ, จำกัดสิทธิ์เฉพาะตารางที่ admin เลือก (`allowed_tables`), ห้ามใช้ credential ที่มีสิทธิ์ DDL/DML |
| API key ของ LLM (OpenRouter) | เก็บแบบ encrypted ต่อ agent, หมุนเวียน (rotate) ได้จากหน้า settings |
| Audit | ทุกการเชื่อม/แก้ credential ต้องบันทึกใน `audit_logs` (ใครทำ, เมื่อไหร่, กับ resource ไหน) โดยไม่เก็บค่า credential ใน log |

## 3. Multi-tenant Isolation

- ทุก query ที่ agent ยิงออกไป (SQL/vector/file) ต้องผูกกับ `agent_id` → `department_id` เสมอ ไม่มี query แบบ global ที่ไม่กรอง tenant
- ใช้ **Postgres Row-Level Security (RLS)** ผูกกับ `department_id` เป็นชั้นป้องกันเพิ่มจาก application-layer filter (กันกรณี logic ฝั่ง backend มีบั๊ก)
- Vector store (PDF chunks) ต้อง partition เป็น collection/namespace แยกต่อ agent ไม่ใช่รวมกันแล้วกรองด้วย metadata อย่างเดียว
- ทดสอบ isolation เป็นส่วนหนึ่งของ regression test ทุกครั้งที่แก้ query layer (ดูแผนทดสอบ)

## 4. ความปลอดภัยของ SQL Agent

- **Sandbox การรัน query:** บังคับ `LIMIT`, ห้าม query ที่ไม่ใช่ `SELECT`, validate ผ่าน SQL parser ก่อนรันจริง (เช่นตรวจ AST ว่าไม่มี `DROP`/`DELETE`/`UPDATE`/`;--` ผสมอยู่)
- **Whitelist ตาราง/คอลัมน์:** agent มองเห็นเฉพาะตารางที่ department admin เลือกให้ตอนตั้งค่า data source
- **Timeout และ resource limit:** จำกัดเวลารันและขนาดผลลัพธ์ กัน query หนักกระทบ production database ของลูกค้า
- แนะนำให้ admin ต่อ **read replica** แยกจาก production database ถ้าเป็นไปได้ ไม่ใช่ต่อ production โดยตรง

## 5. Prompt Injection และการป้องกัน LLM ถูกหลอก

- แยก system prompt (ควบคุมโดย admin) กับ user input/ข้อมูลที่ดึงมาจาก RAG อย่างชัดเจน ไม่ให้เนื้อหาที่ดึงมาจาก PDF/DB ถูกตีความเป็นคำสั่งของระบบ
- Validate output ก่อนส่งกลับ โดยเฉพาะ embed widget: ตรวจว่า agent ไม่หลุด scope (เช่น ไม่เปิดเผย system prompt, ไม่พูดเรื่องนอกขอบเขตสินค้า)
- จำกัดไม่ให้ agent ที่ตั้งไว้สำหรับ public widget เข้าถึง SQL agent แบบ free-form โดยตรง — ควรมี view/cache ที่ปลอดภัยกว่าให้ query แทนการต่อ production DB ตรง ๆ

## 6. ความปลอดภัยของ Embed Widget (Public-facing)

| ประเด็น | มาตรการ |
|---|---|
| Rate limiting | จำกัดจำนวน request ต่อ IP/session ต่อนาที (ตั้งค่าได้ต่อ widget ผ่าน `rate_limit_per_min`) |
| Domain whitelist | ตรวจ origin/CORS กับ `allowed_domains` ที่ admin ตั้งไว้ ป้องกันคนเอา widget key ไปใช้เว็บอื่น |
| Widget key | สุ่มไม่ให้เดาได้ (UUID/random token), revoke ได้ทันทีจากหน้า settings โดยไม่กระทบ internal chat ของ agent เดียวกัน |
| Cost control | ตั้ง budget cap ต่อ agent/widget และ auto-pause เมื่อเกินงบที่กำหนด |
| ข้อมูลอ่อนไหว | Agent ที่เปิดใช้ public widget ต้อง **ไม่** เชื่อมกับ data source ที่มีข้อมูลลูกค้า/พนักงานภายใน — จำกัดเฉพาะข้อมูลสินค้าสาธารณะ |

## 7. Authentication และสิทธิ์การใช้งาน (Internal)

- Pilot ใช้บัญชีภายใน: password hash ด้วย Argon2id, secure HttpOnly session, session expiry/rotation, login rate limit และบังคับ MFA สำหรับ local Super Admin
- Microsoft Entra ID/Microsoft 365 SSO พัฒนาในลำดับถัดไป โดยเตรียม identity model ให้ link กับบัญชีเดิมได้อย่างปลอดภัย
- Role-based access: super_admin / department_admin / member ตาม `agent_permissions` (owner/editor/viewer)
- Department admin แก้ไข config ได้เฉพาะ agent ของแผนกตัวเอง ตรวจสิทธิ์ทุก API call ฝั่ง backend ไม่พึ่งการซ่อนปุ่มฝั่ง frontend อย่างเดียว

## 8. การปฏิบัติตามกฎหมายข้อมูลส่วนบุคคล (PDPA)

- ถ้า data source มีข้อมูลส่วนบุคคลของลูกค้า (เช่น ชื่อ/เบอร์โทรในตาราง order) ต้องมี data minimization — agent ไม่ควรดึงคอลัมน์ PII มาแสดงในคำตอบเกินความจำเป็น
- แจ้งผู้ใช้ embed widget (สาธารณะ) ว่าการสนทนาอาจถูกบันทึกไว้เพื่อพัฒนาบริการ
- กำหนดนโยบายเก็บ/ลบ log การสนทนา (retention period) และช่องทางให้ผู้ใช้ขอลบข้อมูลของตน

## 9. Incident Response

- Audit log ต้องเพียงพอให้ตรวจสอบย้อนหลังได้ว่า agent ไหนเข้าถึงข้อมูลอะไรเมื่อไหร่
- มี runbook สำหรับกรณี credential รั่ว: revoke key ทันที, force re-authenticate, แจ้ง department admin ที่เกี่ยวข้อง
- มี kill switch ระดับ agent และระดับ department ให้ super admin ปิดการใช้งานฉุกเฉินได้ทันที (ใช้ `status: disabled` ที่ออกแบบไว้ใน data model)

## 10. Checklist ก่อน Launch

- [ ] Penetration test เบื้องต้นบน SQL agent (SQL injection ผ่าน natural language)
- [ ] ทดสอบ tenant isolation ข้ามแผนก (ดูแผนทดสอบข้อ 4)
- [ ] ทดสอบ prompt injection บน RAG agent และ public widget
- [ ] Review สิทธิ์ MySQL user ที่ระบบใช้เชื่อมต่อทุกตัวว่าเป็น read-only จริง
- [ ] ตรวจ rate limit และ budget cap ของทุก embed widget ที่เปิดใช้งาน
- [ ] Review การ encrypt credential ทั้งหมดใน database
