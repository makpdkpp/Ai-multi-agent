# แผนทดสอบ — Multi-Agent AI Q&A Platform

## 1. กลยุทธ์การทดสอบโดยรวม

ระบบนี้มี 3 ชั้นที่ต้องทดสอบต่างกัน: (1) ระบบซอฟต์แวร์ทั่วไป (auth, CRUD, UI) ใช้วิธีทดสอบมาตรฐาน (2) ตัว AI agent ที่ผลลัพธ์ไม่ deterministic ต้องใช้ **evaluation set** วัดความแม่นยำแทนการเทียบ output ตรง ๆ (3) ความปลอดภัยของ multi-tenant และ public-facing widget ต้องมี security test แยกเฉพาะ

## 2. Unit & Integration Testing

| ส่วน | ขอบเขตทดสอบ |
|---|---|
| Auth & permissions | login, JWT expiry, role-based access ต่อ endpoint ทุกตัว |
| Data model / API | CRUD ของ agents, data_sources, llm_configs — รวม edge case เช่นลบ agent ที่มี conversation อยู่ |
| SQL agent | แปลงคำถามตัวอย่างเป็น SQL, ตรวจ query ที่ validator ต้อง reject (DROP/DELETE/UPDATE ที่แฝงมา) |
| Data agent (Excel) | อ่านไฟล์ Excel หลายรูปแบบ (multi-sheet, merged cell, หัวตารางไม่อยู่แถวแรก) |
| RAG agent (PDF) | chunking, embedding, retrieval คืนค่า chunk ที่เกี่ยวข้องจริง |
| Token/cost calculation | คำนวณ cost จาก input/output tokens ตรงกับ `model_pricing` ทุก provider รวมกรณี local = ฿0 |

## 3. Agent Evaluation (คุณภาพคำตอบ)

เนื่องจากคำตอบของ LLM ไม่ deterministic ต้องสร้าง **golden dataset** แยกตาม agent แล้ววัดด้วย metric เฉพาะ ไม่ใช่ unit test แบบ exact-match ทั่วไป

### SQL agent
- เตรียมชุดคำถาม-คำตอบที่ถูกต้อง (question → expected SQL หรือ expected result) อย่างน้อย 50-100 คู่ ครอบคลุม schema จริงของแต่ละแผนก
- วัด **execution accuracy** (รัน SQL ที่ agent สร้างแล้วเทียบผลลัพธ์กับ expected result ไม่ใช่เทียบ SQL string ตรง ๆ เพราะเขียนได้หลายแบบ)
- ทดสอบคำถามกำกวม/ไม่มีคำตอบในข้อมูล → agent ต้องตอบว่าไม่พบข้อมูล ไม่ใช่ "เดา" คำตอบ (hallucination check)

### RAG agent (PDF คู่มือสินค้า)
- เตรียมคำถามที่คำตอบอยู่ในคู่มือจริง วัด **retrieval recall** (ดึง chunk ที่ถูกต้องมาได้ไหม) แยกจาก **answer correctness** (สรุปคำตอบถูกไหม)
- ทดสอบคู่มือที่มีตาราง/รูปภาพปนกับข้อความ ว่า chunking strategy จัดการได้ดีแค่ไหน
- ทดสอบคำถามที่คำตอบไม่อยู่ในคู่มือเลย → ต้องปฏิเสธตอบ ไม่ปั้นคำตอบ

### Coordinator (routing)
- ทดสอบว่าคำถามแต่ละแบบถูก route ไป agent ที่ถูกต้อง (MySQL vs Excel vs PDF)
- ทดสอบคำถามที่ต้องใช้หลายแหล่งข้อมูลพร้อมกัน (fan-out) ว่ารวมคำตอบได้สมเหตุสมผล

**เกณฑ์ผ่าน (แนะนำเริ่มต้น):** execution accuracy ของ SQL agent ≥ 90%, retrieval recall ของ RAG agent ≥ 85% — ปรับตามความเสี่ยงของ use case จริงก่อน launch

## 4. Multi-Tenant Isolation Testing

จุดที่พลาดแล้วเสียหายรุนแรงที่สุด ต้องทดสอบเฉพาะเจาะจง:

- สร้าง 2 แผนกทดสอบที่มีข้อมูลต่างกันชัดเจน → ยิงคำถามผ่าน agent ของแผนก A แล้วยืนยันว่าไม่มีทางเห็นข้อมูลของแผนก B แม้จะพยายาม prompt inject ให้ข้าม scope
- ทดสอบ RLS policy โดยตรงระดับ database (query ด้วย role ของแผนก A แล้วพยายามอ่านแถวของแผนก B)
- ทดสอบ vector store: ค้นหาด้วย query ที่ควร match เนื้อหาของแผนก B แต่ยิงผ่าน agent แผนก A ต้องไม่คืนผลลัพธ์ข้ามแผนก
- ทดสอบสิทธิ์ department_admin ว่าแก้ไข/มองเห็น agent ของแผนกอื่นไม่ได้แม้ผ่าน API ตรง (ไม่ใช่แค่ซ่อนปุ่ม UI)

## 5. Security Testing

- **SQL injection ผ่านภาษาธรรมชาติ:** ลองพิมพ์คำถามที่พยายามหลอกให้ agent สร้าง query อันตราย (เช่น ขอให้ "ลบข้อมูลทั้งหมด" หรือ query ที่แฝง `; DROP TABLE`) → ต้องถูก validator บล็อกทุกครั้ง
- **Prompt injection:** ทดสอบทั้งจาก user input โดยตรง และจากเนื้อหาที่ฝังในเอกสาร PDF ที่อัปโหลด (indirect injection) ว่า agent ไม่ทำตามคำสั่งที่แฝงมา
- **Credential exposure:** ตรวจ log, error message, API response ว่าไม่มี credential/API key หลุดออกมาแม้ตอน error
- **Embed widget abuse:** ทดสอบ rate limit จริง (ยิง request รัวๆ), ทดสอบ CORS จาก domain ที่ไม่ได้ whitelist, ทดสอบ widget key ที่ revoke แล้วต้องใช้ไม่ได้ทันที
- **Auth bypass:** พยายามเข้าถึง endpoint ของ super admin ด้วย token ของ department_admin และในทางกลับกัน

## 6. Performance & Load Testing

- Load test SQL agent ภายใต้คำถามพร้อมกันหลาย session ว่า query timeout/connection pool รับมือไหว
- ทดสอบ embed widget ภายใต้ traffic สูง (จำลอง viral moment บนเว็บลูกค้า) ว่า rate limiting และ budget cap ทำงานถูกต้องโดยไม่ทำให้ระบบล่ม
- วัด latency end-to-end ของแต่ละ agent (SQL/Excel/RAG) แยกกัน เพื่อหา bottleneck ก่อนรวม pipeline

## 7. User Acceptance Testing (UAT)

- ให้ department admin จริง 2-3 คน ทดลองสร้าง agent ครบ flow (เชื่อมข้อมูล → เลือก LLM → ทดสอบแชท → ฝัง widget) แล้วเก็บ feedback
- ให้พนักงานในแผนกทดลองใช้ internal chat กับคำถามจริงที่ใช้งานประจำ
- ทดสอบ embed widget บนเว็บไซต์ตัวอย่างจริงจากมุมมองผู้ใช้ภายนอก

## 8. Regression Testing

- ทุกครั้งที่แก้ coordinator/routing logic หรือ prompt ของ agent ตัวไหน ต้องรัน golden dataset ทั้งหมดซ้ำ (ข้อ 3) ก่อน deploy เพื่อจับ regression ด้านความแม่นยำ
- ทุกครั้งที่แก้ query layer หรือ permission logic ต้องรัน isolation test (ข้อ 4) ซ้ำเสมอ — ไม่ข้ามแม้เป็นการแก้เล็กน้อย

## 9. Checklist ก่อน Launch

- [ ] Unit/integration test ผ่านทั้งหมด, coverage ครอบคลุม critical path
- [ ] Agent evaluation ผ่านเกณฑ์ที่ตั้งไว้ (ข้อ 3)
- [ ] Isolation test ผ่านครบทุก scenario (ข้อ 4)
- [ ] Security test ผ่านครบ (ข้อ 5) ไม่มี finding ระดับ critical/high ค้างอยู่
- [ ] Load test ผ่านตาม traffic ที่คาดการณ์ไว้
- [ ] UAT ได้ sign-off จาก department admin ตัวแทนอย่างน้อย 1 แผนก
